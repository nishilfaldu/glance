Example

See a pull request before you read it.

Glance maps a branch: where the changes sit, how the changed functions call each other, and which lines match a risky pattern.

$ pnpm add -g github:nishilfaldu/glance
Open the example How it works

Repo map

The whole repo on one screen. Changed files open up to show the functions the branch touched. Click one to mark it reviewed.

Call graph

Only the paths that lead to a change. Lines are folders, arrows are calls. Hover a function to trace it.

Run it

Check out a branch and run glance. The page opens on localhost and nothing leaves your machine. Add --working to include uncommitted changes.

Share it

Nothing leaves your machine until you publish. glance publish --pr uploads the brief to your own Vercel Blob store and puts the link in the PR description. The store and id sit after the #, so this site never sees them. Publishing again updates the same link. Only names and calls are uploaded, never code.

Under the hood

How it works

No AI. Glance reads git and parses your code with the TypeScript compiler, so the same branch always gives the same map. Here's the whole trip, using the example above.

Where the branch starts

Diffing against main's latest commit would mix in everything merged since you branched. So Glance asks git for the merge base, the last commit your branch and main share, and compares from there.

Main is origin's default branch, then main or master. --base picks another.

Reading the diff

git diff --name-status -M lists each file as added, modified or renamed. Deleted files are gone at the head, so they're left out.

Some files are noise: lockfiles, minified bundles, files that say @generated or DO NOT EDIT in their first lines, and anything under skip: in .glance.yml. They stay on the map, dashed, but aren't read. For the rest, -U0 drops the context lines, so every hunk header points at exactly the lines that changed.

Lines become functions

Each changed file goes through the TypeScript compiler's parser: no build, no tsconfig, no type checking, so any TS or JS file works as it is. A function is a declaration, an arrow function with a name, a class method, a route handler keyed like "POST /session", or a test case it("…", () => …).

An added line belongs to the innermost function around it, and a removed line to whatever now sits where it was. Lines outside any function belong to the file. If main's copy of the file already had a function by that name, it's changed; otherwise it's new. In package.json, each dependency whose version moved gets its own chip.

Calls connect them

Inside each function, Glance collects what it calls: foo(), new Foo(), <Foo />, and ns.foo() through import * as ns. A name is looked up in the same file first, then in the imports. A relative import is tried with each extension and as a folder's index; a package lands on its chip in the nearest package.json.

When both ends changed, the call graph draws an arrow. db.insert() isn't followed: knowing what db is takes type information, and Glance never runs the type checker.

Flags

Rules only read lines the branch added. Two are patterns on a line: a process.env read with a literal fallback, and as any, @ts-ignore or eslint-disable. Two need more than a line: a catch that's empty or just returns null, [] and the like, found in the syntax tree; and in tests, an expect or assert line that was removed and not added back.

Each rule keeps one number across the page; click a numbered chip and the bar at the bottom names its rule. A flag says what was found, not that it's wrong.

What gets written

All of it lands in one JSON file, the brief: the folder tree, each file's state, the touched functions with their calls, and the flags. Names only, never a line of source. The local page reads it from memory, and glance publish uploads exactly this file. Run glance json to see yours.

Drawing it

The page is one HTML file: no framework, no graph library. The repo map is nested boxes that wrap like text. The call graph puts folders, files and functions in columns. Each column starts just past the widest label in the one before, every function gets its own row, and each parent sits centered on its children.

Lines are SVG curves. Calls bend out to the right of the function column, so they never cross the tree.

Limits

Functions are found in TypeScript and JavaScript only. Calls on objects (db.insert()), class methods, functions passed as callbacks, path aliases (@/lib) and imports between packages in a monorepo aren't followed yet. Deleted files don't show up yet.
