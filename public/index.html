Glance
How it works Reference Example
    glance · CLI for TypeScript & JavaScript

    See a pull request before you read it.

    Glance turns a branch into a review map: where the changes sit in the codebase, and how the changed functions call each other. Changes that don't connect to anything stand out on their own.

    $ git clone https://github.com/nishilfaldu/glance
$ cd glance/cli && npm install && npm link
    Open the example How it works

    Why

    AI agents write pull requests faster than people can read them. A forty-file PR shows up, GitHub lists the files alphabetically, and you start at the top. Somewhere around file twelve you lose the thread, skim the rest, and merge.

    The list order is the problem. The change that matters sits between a renamed import and a lockfile, and the one edit that has nothing to do with the task looks like every other file.

    Glance doesn't review the code for you. It gives you a map, so you can start at the main change, follow its calls, and see the leftovers. A quick review beats no review.

    The two views

    Each Glance page has two tabs. They show the same chips: one per touched function, with the same numbers on the same flags, so you can switch views without losing your place.

    Repo map

    The whole repository on one screen, folder by folder. Unchanged files are grey. Changed files open up to show the functions the branch touched, and the scrolling GitHub sidebar isn't needed.

    • A green dot marks a new file or function.
    • An orange number marks a flag. A blue number marks code that isn't connected to the main change.
    • Dashed chips are files Glance skipped, like lockfiles and generated code.
    • Folders that only hold one folder fold together, like src/components/ui. After twelve unchanged files, a folder shows +N more.

    Click a function and press Mark reviewed. It fades in place, and a file fades once all its functions are done. Marks are stored in your browser only.

    Call graph

    Only the paths that lead to changed files, drawn as a tree from their closest common folder. Grey lines are the folder structure. Bold arrows are calls between touched functions.

    Arrows from test cases are hidden until you hover the test, since one test usually calls into everything. Hover any function to light up its calls and dim the rest.

    Quick start

    You need Node 20 or newer. Install the CLI once from a clone:

    $ cd glance/cli && npm install && npm link

    Then, in any repo, check out the branch you want to review and run glance. It compares the branch with the repo's default branch and opens the page in your browser. The page is served from 127.0.0.1 and nothing is uploaded.

    $ glance

    Reviewing your own work before you commit it? glance --working includes staged, unstaged and untracked changes.

    How it works

    Glance is deterministic. There's no model in the loop: the same branch gives the same map every time. It reads git and parses your code with the TypeScript compiler, and every flag comes from a rule you can read.

    The steps are on the right. The sections below go through them one at a time, using the sample pull request: Rotate sessions across checkout, in a small storefront app.

    01

    Finding the touched functions

    Glance diffs the branch against its merge base with the default branch, so commits that landed on main in the meantime don't show up as changes.

    Each changed file is parsed into units, the pieces a reviewer reads as one thing:

    • function declarations, and arrow or function expressions assigned to a name
    • class methods, shown as Class.method()
    • route handlers keyed by an HTTP method and path, like "POST /session/refresh"
    • test cases: it("…") and test("…") with a callback

    Every added line, and the spot where every removed line used to be, is assigned to the innermost unit that contains it. Those units are the touched functions. A unit whose name didn't exist in the base version of the file is marked new.

    Lines outside any function, like a top-level constant, belong to the file. If a rule flags one of them, the number goes on the file chip.

    02

    Following calls

    While parsing, Glance records every call inside each unit, including new Thing() and JSX like <Button />. Then it works out where each call lands:

    • a plain name is looked up in the same file first, then in the file's imports
    • named, default and import * as ns imports are all followed, so ns.fn() resolves too
    • relative paths are tried with each TS/JS extension and as a folder's index file
    • a package import, like jose, lands on that dependency's chip when the branch added or changed it in the nearest package.json

    Calls between two touched functions become arrows. Every function in a changed file counts toward connecting them, so when A() calls an unchanged helper that calls B(), A and B still end up in the same group. Only A and B are drawn.

    03

    Finding the main change

    Glance treats calls as links in both directions and splits the touched functions into connected groups. The largest group is the main change. Each touched function outside it gets a blue flag: not connected to the main change.

    Tests don't count toward this. A test calls into everything it covers, so letting tests connect groups would glue unrelated edits together. Test cases still show their calls in the call graph.

    In the sample, six functions form the session work. formatRelative() and apiFetch() were changed too, but nothing in the main change reaches them. That doesn't make them wrong. It does make them worth asking about, because an agent that was told to rotate sessions also edited a date formatter.

    04

    Flags

    A flag says what a rule found, not whether it's a problem. Rules only look at lines the branch added, except the assertion rule, which looks at removed lines in test files. Code that was already there doesn't get flagged.

    Flags are numbered top to bottom in the order the map draws them, and the numbers are the same in both views. When you read the PR on GitHub afterwards, "③" means the same thing everywhere.

    New and changed dependencies aren't flags. Each one gets its own chip under package.json, so a new package is something you review, like a function.

    05

    What gets skipped

    Some files change in every PR and say nothing about it. Glance still shows them on the map, as dashed chips you can click, but it doesn't parse them or count them as functions to review.

    To skip more, add a .glance.yml to the repo root with a list of globs. * matches within a folder and ** matches across folders.

    Deleted files don't appear, because the map shows the repo as it is at the head of the branch.

    Sharing a link

    glance publish uploads the brief and prints a link. Add --pr and it also writes the link into the pull request's description through the GitHub CLI, using the PR's title for the page.

    $ glance publish --pr

    Each branch keeps one link. The id is saved in .git/glance/briefs.json, so publishing again after a push updates the same page, and the PR description keeps a single marked block that gets replaced, not appended to.

    What's uploaded. The brief holds folder and file names, the names of touched functions, which calls which, and the flags. It doesn't hold source code or diffs.

    Who can see it. Anyone with the link. Links use a random 128-bit id, are kept out of search engines, and send no referrer. Briefs are stored in a private bucket and are only readable through the page.

    --working can't be published. Commit and push first, so the link matches what's on the PR.

    Reference

    Commands

    CommandWhat it does
    glanceBuilds the brief and opens it on a local page.
    glance publishUploads the brief and prints its secret link.
    glance jsonPrints the brief as JSON, for scripts or your own viewer.

    Options

    OptionDefault
    --base <ref>Branch to compare against. Defaults to origin's default branch, then main or master.
    --head <ref>Commit or branch to review. Defaults to HEAD.
    --workingInclude uncommitted and untracked changes. Local only.
    --title <text>Page title. Defaults to the PR title with --pr, else the branch's first commit message.
    --pr [number]With publish: link the page on this branch's PR, or PR number. Needs gh.
    --port <n>Port for the local page. Defaults to any free port.
    --no-openStart the local page without opening a browser.

    Configuration

    Two files, both optional until you publish:

    • .glance.yml in the repo you're reviewing, for extra skip patterns.
    • ~/.config/glance/config.json on your machine, with the site to publish to and its key. Keep it private with chmod 600.

    GLANCE_URL and GLANCE_PUBLISH_KEY override the file, which is handy in scripts.

    Limits

    Glance is young and says so. What it doesn't do yet:

    • It finds functions in TypeScript and JavaScript only (.ts, .tsx, .js, .jsx, .mjs and friends). Other changed files show up as one chip you review as a whole.
    • Calls on objects, like db.sessions.insert(), aren't followed. Neither are path aliases like @/lib/auth, re-exports through an index file, or dynamic import().
    • Functions are the smallest unit. Changed types and constants count toward their file.
    • It doesn't run tests or read CI. That's CI's job.
    • A brief can be up to 4 MB.

    Self-hosting

    The site is a static viewer plus two small functions, deployed on Vercel from the same repo as the CLI. To publish to your own:

    • Import the repo into Vercel. There's no build step: public/ is served as is.
    • Connect a private Blob store to the project. Vercel adds BLOB_READ_WRITE_TOKEN for you.
    • Set GLANCE_PUBLISH_KEY to a long random string, like the output of openssl rand -base64 32.
    • Put your URL and the same key in ~/.config/glance/config.json.

    The key only allows writing. Reading a brief needs its id, and the Blob credentials never leave Vercel.
